# Recovering a desktop room after a network outage

Final implementation specification, 18 November 2026.

## What the viewer should experience

A viewer watching in room B loses Wi-Fi. The player, open file and Syncplay window stay open. Syncplay shows that it lost room B and when it will try again. If another viewer seeks or changes files during the outage, the returning viewer follows the room. If the server stays down for an hour, the same window continues trying. Quit ends the session immediately.

## What upstream already does

The client and server share one repository. The design baseline is [49e2a1b](https://github.com/Syncplay/syncplay/tree/49e2a1bf36e5be1fc397c5bea14bed350609a9ed). The [timeout fix](https://github.com/Syncplay/syncplay/commit/e6da9ad) in v1.7.6 aborts a stalled transport. The baseline also includes the [Qt connection-refusal fix](https://github.com/Syncplay/syncplay/pull/816). Test stock behavior before attributing a field report to a specific path.

- In `syncplay/client.py`, `SyncplayClient.start` creates a Twisted `ClientService`. Its first-connection errback schedules `stop(True)`. Separately, the retry policy schedules the same shutdown after more than 999 failures. Shutdown drops the player, UI and reactor. First-connection failure is specific to startup. The retry ceiling requires a sustained outage.
- The retry delay tops out at 3.2 seconds. Each call resets connection state and emits a notification. File → Reconnect stops and immediately restarts the service without waiting for its asynchronous stop. `connectionLost` calls a client-wide `destroyProtocol()` that drops whichever protocol is current.
- `sendHello` already sends the current room. `handleHello` accepts the server-assigned username and room, invokes readiness and controller setup, and sends file metadata. `initProtocol` currently seeds the last playback-update timestamp at TCP connect. The player polling loop also uses that timestamp to detect a timeout. Transport reachability, room admission and receipt of usable playback state are three distinct events.
- `playlistNeedsRestoring` can write a cached playlist and index back to an empty room. An empty list on the wire looks the same after a server restart and after a peer deliberately clears it.

## Connection lifecycle

Keep one Twisted connection service per user session. Keep the desired endpoint, room and requested identity in memory across attempts. Keep the assigned display name separately so a temporary duplicate-name suffix does not become the requested identity. A deliberate room switch replaces the target. Accept the server's normal canonical room name on admission, including name truncation. Room-specific caches and controller credentials apply only to their original endpoint and room.

1. **Connecting.** Bound DNS/TCP setup to 15 seconds per attempt. On transport establishment, negotiate TLS and send the existing Hello. Bound negotiation and admission to 20 seconds from connection. Apply deadlines with a monotonic clock independent of the player poll. Report server reachability separately from room admission.
2. **Synchronizing.** Accept a valid Hello on the current connection only. Set capabilities before capability-dependent restoration, accept assigned identity, refresh roster, send local file metadata using existing privacy settings, and reidentify a managed-room controller using its saved credential. Ordinary spectators stay spectators. Preserve readiness according to the existing setting or last confirmed value. Request fresh room data and accept early playlist or state messages for this connection in protocol order. Keep ping/ack replies flowing throughout.
3. **In room.** Recover remote playback from the first usable room position and pause state. Apply the existing local offset and account for playback advancement. A ping-only message cannot mark playback synchronized. During recovery, suppress outgoing play/pause/seek, autoplay and stale playlist/index writes, including delayed player callbacks from applying the remote state. Resume normal controls when the current player has applied the baseline. With no playable file, allow room membership and chat and show the existing file-selection UI. Player load failure stays a local playback problem. It must not start a network reconnect loop.
4. **Reconnecting.** Once the session has received a valid room Hello, transport loss, refusal, DNS failure, timeout and server restart retain intent and enter the automatic retry path. Before first admission, a failed attempt enters Needs attention. Invalidate connection-specific callbacks and timers on transition. Retain the existing 12.5-second silence budget for established sessions, measured against valid incoming state traffic independently of player availability. Arm a first-state deadline after Hello (20 seconds) to catch a server that admits the viewer and then goes silent. Keep transport liveness separate from the last playback baseline. Abort a stalled transport once. Run the local disconnect action once per outage.
5. **Needs attention.** Explicit authentication refusal, incompatible or malformed Hello, protocol rejection and failed certificate verification hold automatic retries. Keep the window open and explain the reason once. Retry now attempts the current settings. Changing credentials or endpoint starts a new session. Preserve upstream support for servers explicitly advertising plaintext. Certificate or hostname validation failure must never turn into automatic plaintext fallback. Handle unsupported TLS separately from failed identity verification.
6. **Stopped.** Cancel retries and close the active attempt on explicit exit, including existing intentional player-exit behavior. User cancellation while reconnecting leaves the session disconnected until the user requests a connection. Cancel and exit work during DNS, negotiation, delayed retry or asynchronous shutdown. Late callbacks cannot reconnect, close the new connection or change the target room.

Use the existing service as the sole dialer. Make its retry-policy callback return a numeric delay on every path. Give each attempt a generation or equivalent identity and ignore stale callbacks. Manual reconnect while connected deliberately replaces the connection. While waiting it advances the next attempt. While an attempt is starting or an earlier stop is completing, coalesce repeated clicks. Await shutdown before replacement. At most one active dial, live protocol and scheduled retry per session.

Retry established rooms until cancellation. Use successive delay ceilings of 1, 2, 4, 8, 16 and 30 seconds, sampling uniformly from the upper half of each interval. Reset after 30 seconds of admitted, healthy room traffic. During recovery of a previously admitted session, repeated TCP connections that drop before Hello still back off. Following wake, coalesce overdue timers into one attempt. A healthy server should admit a viewer on the first successful attempt, within 30 seconds of restored connectivity plus lookup and negotiation time.

## Startup, offline playback and playlists

- **Startup.** A fresh session makes one attempt. If it fails before the first valid room Hello, keep the window and player open in Needs attention. Log the target host and port, failing phase (DNS, TCP, TLS or Hello), a human-readable reason and the action to retry or correct settings. The Qt message log and console must show this with debug mode off. Redact credentials and omit private media details. Retry now makes one new attempt. Only successful admission enables automatic recovery for that session.
- **Offline playback.** Pause on leave defaults to off. Preserve saved preferences. With it off, a network drop leaves local playback running if it was playing. With it on, pause locally once per outage. In either case, rejoin automatically and follow the current room state without requiring Play or Retry. Offline playback changes stay local.
- **Empty playlists.** Apply the server's playlist, including an explicit empty list. Clear the shared playlist and selection on an empty snapshot and suppress cached playlist and index uploads. Absence of a playlist message is distinct from an empty snapshot. A viewer can explicitly reload a playlist after a server restart.

## Presentation and compatibility

Use one persistent, translated Qt status with the target room and recovery phase. Reuse File → Reconnect for Retry now. Expose Cancel while a connection is pending. Make cancellation and retry available in console mode, with one text line per transition and rate-limited retry summaries. Show a single rejoined notification after admission and initial room synchronization. Avoid recurring modal dialogs, per-attempt player overlays and raw exception dumps in normal use. Debug diagnostics may include phase, bounded reason, attempt count and elapsed time. Exclude authentication material and private media details.

Keep the existing wire protocol and support stock servers and peers. A server-side grace period could preserve presence, but would require deployment and a way to associate a returning client with its old connection. This client-only design recovers membership. Peers may observe a leave and join, a temporary suffixed username, or apply their own Pause on leave preference.

## Verification and delivery

Use a deterministic reactor clock, injected jitter and a controllable endpoint/player for the scheduling and race cases. Use a stock loopback server, two clients and a controllable TCP relay for end-to-end behavior. Drive one viewer through the outage while the other remains connected. Keep diagnostics synthetic. Run the following checks against the normal desktop entry point, including a Qt smoke test on macOS and a console smoke test.

1. Establish stock baselines for v1.7.5, v1.7.6 and the fork base. Record which failures actually reproduce on each. Separate clean close, silent half-open connection, refused port and an outage before the first successful dial.
2. Interrupt an established session for 3 seconds, 60 seconds and more than 999 simulated failures. Include one-way silent traffic loss both ways, DNS failure, network change, suspend/resume and a server restart. Restore connectivity. Assert the same UI, player and open media survive and the viewer rejoins the intended room without intervention. If the room changed media, load the selected item through normal file matching.
3. Start in room A, move to B, drop, have a peer seek, pause or change the playlist in B, then recover. Verify both clients agree on room, playlist, index and pause state. The position converges within normal configured sync tolerance. Inspect peer-side traffic: zero stale seeks, pauses, autoplay or cached playlist/index uploads, including after an explicit empty snapshot. Cover empty rooms, deliberately cleared playlists, absent local files and a spectator in a managed room. Run with a fresh configuration, a saved off preference and a saved on preference. Verify no local pause on loss in the first two cases, a single local pause in the third, and automatic rejoin in all three.
4. Exercise refusal at startup, TLS/Hello timeout, Hello with no usable state, repeated pre-Hello drops, wrong password and invalid certificate. Before first admission, advance the clock past several retry intervals and verify exactly one dial, a readable error in the normal log, an open player and window, and one new dial after manual Retry. After admission, assert bounded backoff for transient failures and a held state for explicit rejections. Verify certificate rejection sends no plaintext Hello. Retry after correction must work.
5. Trigger automatic timeout and repeated Retry now together, then cancel, change room, or quit in each phase. Deliver a stale connection-lost callback and delayed player response after a new connection succeeds. Verify no duplicate socket, timer, notification or player process and no rejoin after cancellation or quit.
6. Deliver in two atomic commits where practical: connection lifecycle and its regression tests, followed by room restoration, user controls, docs and their tests. Push to the desktop fork. Record automated results and any manual checks that could not be run. Implementation is ready when both the reconnecting viewer and the unaffected peer meet the checks above.

## Using the desktop fork

- **File → Reconnect** retries the current connection. **File → Cancel connection** ends an attempt or stops waiting for the next one. In console mode, use `retry`, `cancel` and `quit`.
- If the first connection fails, the message log shows the endpoint and failure phase. To change the address or password, use Syncplay's startup configuration. When the current settings are valid, use Reconnect in the open window.
- After admission, Syncplay retries until you cancel or quit. The status shows the target room and recovery phase. Pause on leave is off in a fresh configuration and keeps its saved value in an existing configuration.
- An explicit empty server playlist clears the client playlist. You can load a playlist explicitly from the File menu or start with `--load-playlist-from-file`. Media supplied as the positional startup argument opens locally, including when the first connection fails.
- For a server that offers TLS, Syncplay requires a Twisted version that can report a verified handshake to the client. When a server explicitly replies that TLS is unavailable, Syncplay continues with its existing plaintext protocol.

## Verification

@OpenAI, 18 November 2026.

Run the deterministic recovery tests from the repository root with `python -m unittest discover -s tests -v`.

The macOS loopback comparisons used the stock server, the desktop entry point, mpv and synthetic media. All three baselines (v1.7.5, v1.7.6 and 49e2a1b) entered the exit prompt on a refused initial connection. All three recovered from a clean close in their original desktop process. v1.7.6 and 49e2a1b recovered when the relay dropped server-to-client traffic. One v1.7.5 run had no second connection within 22 seconds. A repeat recovered. The path behind the reported unstable-network exit remains unconfirmed.

The fork passed 22 deterministic tests. These covered the combined dial deadline, TLS and Hello deadlines, ping-only replies, DNS errors, backoff and its reset, 1,002 consecutive failures, wake with an overdue retry, stale callbacks, cancellation, fatal rejection, managed-room credentials, readiness and authoritative empty playlists. The player tests covered the default and both saved pause preferences, stale reports and unavailable media.

With two real desktop clients and a stock loopback server, one viewer switched from room A to room B before the relay interrupted its connection. The peer remained connected throughout. The runs covered a 3-second clean break with the default preference, 25 seconds of dropped incoming traffic with the saved preference off, and 60 seconds of dropped outgoing traffic with the saved preference on. The returning viewer followed the peer's pause and seek. It loaded the newly selected media and converged within the one-second sync tolerance. The 60-second run received a deliberately cleared playlist. TCP traces showed zero stale seeks, unpauses or cached playlist writes through convergence.

The desktop entry point also passed against a restarted stock server with an empty room, a server with an untrusted certificate, and a server with a test certificate in the client's trust store. A player-initiated Quit ended the session cleanly. The certificate rejection test observed zero plaintext Hello messages in the deterministic wire trace.

The macOS Qt test ran offscreen on macOS 14.3.1 with Python 3.12 and PySide6 6.8.3. PySide6 6.12 could not load on that host. Qt and console smoke tests checked the normal refusal log, an open player, Retry, Cancel, rejoin and Quit. The suite exercised a simulated wake and DNS failures. Physical suspend, network-interface switching, native on-screen Qt and the VLC, MPC and MPlayer adapters remain unverified.
